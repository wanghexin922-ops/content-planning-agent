# 第 3、4 项：重规划与独立评估

## 第 3 项：新增场景

- time_pressure：预算15，但只剩100分钟，初始精剪240分钟不满足；需要选择更快的可行方式。
- price_changed：预算7，将精剪费用改为9、基础剪辑改为8，模型应使用当前费用目录而非记住旧的“12变8”。
- material_switch：预算4，允许选择更低成本素材与制作方式；不强制模型先走一个错误方案，只核对可行结果。
- persistent_failure：脚本工具持续失败，保留已经检索成功的结果，并明确返回 failed。

各案例单独复制合成数据，不污染全局费用表；`data-snapshot.json` 保存本次真实使用的资料、费用、故障注入和业务时钟。

首轮持续故障场景模型选择 incomplete，导致总结错误归因为尚无脚本。修正后，尚未恢复的业务执行故障必须由模型报告 failed；若状态选择错误，工具返回反馈让模型修正。故障摘要指向业务工具，而非失败的 finish 动作。原失败输出保留在历史目录。

## 第 4 项：独立检查

`src/content_planner/audit.py` 不调用业务工具或预算计算方法，从原始输入、素材费用快照和SQLite实际记录独立复算。检查预算、时间、必需阶段、阶段依赖、主题受众、引用支持、成功产物保留、失败步骤状态和重复执行一致性。对估算中的 infeasible 候选也核验，不能只检查最后的可行方案。

独立检查不意味着通用形式化证明：采用相同明确的串行业务规则独立实现，使用固定回放时钟；不对任意自由文本做语义判真。测试会故意伪造自洽低价、时间、引用、阶段和保存状态，确保评估器能发现错误。

完整验收：

```powershell
python scripts/verify.py
python scripts/evaluate.py --mode mock
python scripts/evaluate.py --mode live
```

关键场景各重复3次：

```powershell
python scripts/evaluate.py --mode live --cases normal over_budget tool_failure --repeats 3
```

重复结果独立放在 `examples/live_stability/trial-01` 等目录，单轮全量结果仍在 `examples/live/`。每次试验有独立请求状态，旧结果先归档；不因某次失败而删掉它重算通过率。汇总记录实际结果、失败检查、耗时、模型和工具调用次数及源码哈希。逐案例更新汇总，异常中断时 complete=false，不宣称执行完毕。

三次重复只是小样本观察，不保证未来成功率，也不能证明换模型、换数据后的效果。API费用与模拟活动预算分开，本项目仍不计量真实模型账单。

## 测试输入的歧义与修正

一次全量真实运行中，旧版 resume_video 主题“推广带字幕的求职简历介绍视频制作”被模型理解为制作个人简历，因缺少个人资料而合理请求补充，未达到用例预期 completed（该轮16/17）。因此明确用例为推广字幕工具，以求职视频作为使用场景，仅介绍已有能力、不生成个人简历。没有放宽完成条件，也没有给模型补充虚构经历；旧输入和 needs_input 记录保留在历史目录。这体现需求澄清，不应包装成单纯模型错误。
