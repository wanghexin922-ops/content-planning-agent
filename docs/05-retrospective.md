# 实现复盘与下一步

## 本次实现遇到的核心问题

最关键的问题是把“模型认为成功”和“业务工具确实成功”分开。模型可以选择动作，但不能作为费用、保存状态和步骤成功的事实来源。本实现让工具拥有确定性计算与写入权限，并在 finish 时检查数据库，测试中强行宣称已保存会被拒绝。

另一个问题是超预算调整与失败续跑的状态一致性：重规划不能抹掉之前失败记录，重试不能丢失成功脚本。持久化工具对话、成功产物与每步结果后，可以从失败观察继续；跨进程测试验证了检索和脚本不会被无故重复执行。

估算结果还具有时间敏感性：某一刻可行不代表保存时仍可行。因此保存必须基于当前时钟再核算。对应测试在估算后推进一分钟，验证临界截止时间下会阻止保存。

## 本实现体现的学习点

- ReAct 的有效证据是模型看到不同观察后做出不同动作，不是使用某个框架名称。
- 幂等需要请求身份、不可变输入和存储唯一性共同支持，单纯“有结果就返回”不足以处理冲突。
- Mock、协议模拟与真实模型运行解决不同验证问题，报告中必须保留边界。
- CLI、固定业务时钟和可执行案例足以提供可复现的评审入口。

以上学习点根据代码与实际运行记录整理，由 AI 辅助归纳。

## 最难的问题与复盘结论

从本次实现与验收记录看，最难的问题是让“生成了方案”“方案满足原需求”和“方案已成功保存”保持一致。首轮真实运行中，即使流程顺利结束，也可能发生偏离主题；因此，成功不能只看模型的结束语，还要核对原始需求、费用、依赖和保存结果。

本次协作的可复用经验是先完成能运行的核心链路，再按验收点逐项补齐证据；遇到失败保留现场和已有产物，用输入、工具观察及下一步动作判断是否确实发生了重规划。这些结论来自项目记录，由 AI 辅助整理，具体实现和调试职责见贡献说明。

## 未完成范围与下一步

当前完成的是 CLI 内容规划闭环。真实素材平台、实际制作发布、多人资源排期、图形界面和生产级分布式运行环境不在本次范围；检索相关性、模板内容质量和长期运行稳定性仍有提升空间。

后续若增加一小时，建议优先补充人工改写的主题和更换素材后的测试，核对来源、预算及是否偏离需求，再根据失败样本改进检索规则。这比只增加功能入口更能检验现有 Agent 的适用范围。还可以记录模型调用 usage，评估真实 API 成本与耗时。

## 实际发现与改进

单测和 Mock 全通过后，真实模型仍会偏离用户主题。首轮无素材案例将量子芯片实验室活动变成字幕产品宣传，说明“保存成功”不能等同于“业务正确”。修正同时覆盖提示与工具边界，以原始主题约束素材适用范围，保留失败样本并重新验收。这是本次真实模型验证最有价值的发现。

本次完善的执行时间、测试数和真实结果写入 examples/refinement-info.json；它仍不是候选人个人投入时间。

## 失败恢复专项复盘

此前的续跑测试偏重达到上限后的继续，不能充分证明失败终态恢复。本次增加明确恢复请求上下文及三个独立进程的真实模型验证，检查旧失败步骤不变、成功脚本不变、方案唯一。另修正 Windows 临时 SQLite 连接未关闭的问题。该阶段通过 53 项测试；后续扩展后的最新测试与真实回归结果见评估报告。

## 独立验证的收获

只核对工具返回的 feasible 和总价相加，可能遗漏同源计算错误。因此增加独立数据复算及自洽伪造金额等反例；持续工具故障的真实试验还揭示终态归因错误，现通过工具反馈让模型改选 failed。关键场景重复次数有限，报告如实区分本次通过率和未来可靠性。
